## Introduction

You will get stuck. A lesson will be unclear, a link will be dead, a project will ask for
something you do not know how to make. This lesson tells you where to go in each case, and
how to turn being stuck into a contribution so the next learner is not.

The course is a public repository. The people who maintain it are learners and working PMs
with jobs. There is no support desk. What there is instead is a community that answers
questions and a very low bar for fixing things yourself.

## Lesson overview

This section contains a general overview of topics that you will learn in this lesson.

- The three places to get help and which to use when.
- How to ask a question that gets answered.
- How to report a broken link or a mistake.
- How to contribute: fixes, resources, whole lessons.

## Where to get help

**Stuck on the material.** Reread the lesson's Assignment items. Most "I don't understand"
moments come from skipping a linked reading. Then search the course's
[Discussions](https://github.com/MuizDebo/open-pm-course/discussions); someone has probably
asked. Then post in the Q&A category with the lesson number in the title.

**Stuck on a project.** Post in that project's thread, not in Q&A. The people who have done
it are already there. Say what you have so far and where it stops.

**Stuck on GitHub itself.** GitHub's own [documentation](https://docs.github.com/en) is
good and searchable. The Hello World guide from lesson 0.2 covers almost everything the
course needs.

**Something is wrong with the course.** Broken link, factual error, confusing paragraph.
That is an issue or a pull request, below, not a question.

## Asking a question that gets answered

Questions in Discussions get answered when they are easy to answer. The pattern:

1. **Lesson number and title** in the subject line. "3.2.2 User interviews: how many is
   enough?" not "Help".
2. **What you are trying to do**, in one sentence.
3. **What you have tried or read**, so nobody repeats it back to you.
4. **The specific thing you are unsure about.** A question with a question mark.

Then, when someone answers, reply. Say whether it helped. Mark the answer if it did. Threads
that end with a marked answer are what the next person finds when they search.

## Reporting problems with the course

Every lesson page has an **Edit page** link at the bottom that opens the lesson's source
file on GitHub. From there:

- **A typo, a dead link, a wrong number.** Click the pencil icon, fix it in the browser, and
  propose the change. GitHub turns that into a pull request. Nobody expects you to know Git.
- **Something bigger, or something you are not sure how to fix.** Open an
  [issue](https://github.com/MuizDebo/open-pm-course/issues/new) describing what is wrong and
  where. Include the lesson number and quote the sentence.

A dead link is the most common problem. The course runs an automatic link check every week,
but external sites move faster than that. If you hit one, report it. Thirty seconds of your
time saves everyone after you.

## Contributing

The course is licensed so that anyone can improve it, and it needs improving. The
[contributing guide](https://github.com/MuizDebo/open-pm-course/blob/main/CONTRIBUTING.md)
has the detail. The short version, from smallest to largest:

- **Fix a typo or a link.** Edit page, fix, propose. Merged within days.
- **Add a resource.** A better article, a clearer video, a talk that changed how you think
  about a topic. Open a pull request adding it to the lesson's Assignment or Additional
  resources, with a sentence on why it belongs. Read the
  [style guide](https://github.com/MuizDebo/open-pm-course/blob/main/LAYOUT_STYLE_GUIDE.md)
  first: every link needs a purpose, and some sources can only be linked, not copied.
- **Write a draft lesson.** Many lessons carry a Draft badge and contain only an outline.
  Pick one you know well, open an issue saying you are taking it, and write it following the
  style guide. This is the highest-value contribution there is, and it is also an excellent
  portfolio piece. Writing a lesson on prioritisation frameworks that strangers then use is
  a stronger interview story than having read about them.
- **Propose a new lesson or project.** Open an issue first. The curriculum map is the
  source of truth, and the sidebar is generated from it, so additions go through the map.
- **Review submissions.** Already covered in lesson 0.3, and it counts.

Everything you contribute is licensed the same way as the rest of the course: CC BY-SA 4.0
for content, MIT for code. Your name goes in the commit history, which is public.

## Ground rules

Short, because they are obvious:

- Be kind and be specific. Both at once.
- Critique work, not people.
- No marketing. Do not add links to things you sell.
- Link, do not copy. Other people's writing stays on their site.

Anyone who cannot manage these will be asked to leave the Discussions.
